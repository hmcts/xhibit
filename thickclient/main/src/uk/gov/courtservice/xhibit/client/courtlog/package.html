This package and it's children provide the functionality to add, change and delete court log events and to view the resultant changes in the court log screen.

Package Structure

Excluding those items described below, there is no specific package structure supported since the majority of user generated court log events are defined in this, the main level.

  • uk.gov.courtservice.xhibit.client.courtlog:
    Contains the components that support the majority of court log events. These in turn are grouped by name thus, files concerning one specific court log event share the same stem (see also Naming Convention below)
    • uk.gov.courtservice.xhibit.client.courtlog.directions:
      Contains components that perform processing specific to directions court log events.
    • uk.gov.courtservice.xhibit.client.courtlog.util:
      Contains components that perform common processing.

Event Types

Generic Events

These court log events may be further categorised by the types of screen components they reveal to the user. These are:

  • SimpleEvent<Dialog/Model/Panel> - where the user is presented with only the freetext, log date and log time screen components. A number of court log events are supported by this mechanism
  • MediumEventMD<Dialog/Model/Panel> - where the user is presented with a date widget plus the freetext, log date and log time screen components. A number of court log events are supported by this mechanism
  • MediumEventML<Dialog/Model/Panel> - where the user is presented with some form of list plus the freetext, log date and log time screen components. A number of court log events are supported by this mechanism
  • MediumEventMT<Dialog/Model/Panel> - where the user is presented with a textbox plus the freetext, log date and log time screen components. A number of court log events are supported by this mechanism

Bespoke Events

These are written to support specific court log events and may consist of a number of textboxes, lists, tables, radio buttons and checkboxes, etc., etc. The file name indicates the event it supports:

  • eventName<Dialog/Model/Panel>

Naming Convention

File names take a predictable form and consist of the following common components shown below with a general description of the use:

  • eventNameDialog - controls the popup dialog box in which the court log event panel sits
  • eventNamePanel - the screen that support the event including all screen components and associated processing
  • eventNameModel - used to pass data to and from the panel/dialog files and the midtier platform. It contains a representation of the data on the screen
  • eventNameTableModel - where applicable, manages the behaviour of a given table component on the panel - where there is more than one table, the name of this file will reflect which table it represents
  • eventNameTableRowModel - where applicable, used to pass data to and from the panel/dialog files and a table component. It contains a representation of the data in the table component

Court Log Events

Components

Court log events that follow the pattern named above extend three bespoke classes and comprise a framework:

  • XDialog - the superclass of the Dialog component
  • XPanel - the superclass of the Panel component
  • FreeTextModel - the superclass of the Model component

The Panel supports a number of life-cycle methods which may be called by the Dialog at various times in response to user input. The table below describes these methods and their uses:
Method Name When Called Typical Use
stepInitialise() Under the control of the developer: the framework will NOT call it.

It is normally called in the panel's constructor after saving any constructor parameters

 Obtain reference data or data that is unlikely to change while the screen is in use.

Where applicable, this data may be saved in the model for later use within panel or to pass to another dialog
stepActivate() Under the control of the framework and is called when the screen is made visible Obtain non-reference data which is normally saved in the model for later use
stepValidate() Called by the framework whenever the OK button is clicked by the user.

Explicit calls may also be made to it from within the panel

 Validation of data on the screen, i.e. client-side only.

If the data is valid, processing may continue.

If there is any error, an exception is thrown
stepDeactivate() Under the control of the framework and called when the screen is made invisible.

Explicit calls should NOT be made to this method from within the panel.

It is called after stepValidate() but only if no validation exception occurred

 Normally used to save data from the screen in the model.

Under some circumstances, it may also be appropriate to make business delegate calls at this time to persist the data
stepDeinitialise(boolean) Under the control of the framework and called whenever the user requests to close the screen, i.e. both OK and Cancel.

Explicit calls should NOT be made to this method from within the panel

 The boolean parameter indicates whether or not data should be persisted.

In some circumstances, for example when the screen is part of a wizard, it may be more appropriate to persist data in the stepDeactivate() method of each panel in the wizard
stepUpdateViewState() After some user interaction with a component on the screen, for example, as part of component listeners, when text has been entered into a text fied, when a row is selected in a table or a command button is clicked.

It is also commonly called as the last step in stepActivate()

 Change the state of the screen depending on available or selected data, e.g. enable/disable screen components.

Enable the OK/Apply, Next/Prev and Finish buttons as and when appropriate
